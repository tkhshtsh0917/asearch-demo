# サーバー側の検索用解析

[English](../search-analysis.md) · 日本語版

表示する質問文と、検索対象となる表現は別のリソースです。固定の質問keyによって、カタログ内の原文とASIX v1内の複数の検索用textを紐づけます。どの表現に一致しても、同じ質問は1件として返します。記事タイトルや回答は検索対象に追加しません。

```text
AutoWikiQAの質問原文 ────────────────────> 表示カタログ
       │                                      │ key
       └─> Sudachi・フィルタ・同義語・ローマ字 ─> texts[]
                                                │
                                        Release版Rust CLI
                                                │
                                            ASIX v1
                                                │
                                 Worker内の読み取り専用WASM
```

## 生成する検索用表現

形態素解析・フィルタ・同義語・ローマ字変換はRust CLIとサーバー専用の`asearch-analyzer` crateが担当します。`tools/analysis`はネットワーク取得、版固定、CLIの呼出しだけを担当します。システム辞書はSudachiDict-core 20261015、ローマ字変換はRustのwana_kana 5.0.0です。Sudachi・各辞書・ローマ字変換器はブラウザへ配信せず、既存のRust正規化と検索だけを実行します。

各文書には原文を先頭に入れ、その後に空でない補助表現を重複除去して登録します。

1. 正規化した内容語を空白で結んだ表現。
2. 内容語のカタカナ読みを空白で結んだ表現。
3. `biitoruzu`のように長音を母音の繰り返しにしたローマ字。
4. `bi-toruzu`のようにカタカナの長音記号を`-`にしたローマ字。
5. 対象トークンから得た独立した同義語。質問全文を同義語ごとにコピーしません。異なるtextをまたいだ複数語の一致は扱いません。

英字の大小・文字幅・ひらがな／カタカナは既存の`ja-basic-v1`で吸収します。`Beatles`はビートルズのローマ字表記ではなく英語名です。固定したSudachiDictのグループ007475に`ビートルズ`・`Beatles`・`The Beatles`が収録されているため、対象質問へ`ビートルズ`・`びーとるず`・`Beatles`・`BEATLES`・`beatles`・`biitoruzu`・`bi-toruzu`で到達できます。

## フィルタと同義語の展開方向

`tools/analysis/policy.json`でSudachiの分割モードCを選び、名詞・動詞・形容詞・形状詞を残します。形状詞は「静か」など、いわゆるナ形容詞を扱うために含めます。stopwordsとstoptagsは、版固定したelasticsearch-sudachiの公開リソースを使います。stoptagsは品詞の階層要素の前方一致、stopwordsは小文字化した表層形・正規化形・辞書形のいずれかで照合します。フィルタは検索用のキーワード・読みと同義語展開の対象選択に適用し、原文の語は削除しません。

これはアプリケーションの方針であり、日本語検索全般に適用できる唯一の規則ではありません。代名詞・助詞・助動詞も原文では引き続き検索可能です。補助表現によって一致範囲は広がり、否定などの区別を失う場合があります。意味の同一性やBM25・フィールド別重み付けを保証する仕組みではありません。別コーパスに適用する際は検索品質を評価してください。

[SudachiDictの同義語ソース](https://github.com/WorksApplications/SudachiDict/blob/830bf9e1313f6f75235ba87ee041e144dbcad8c1/src/main/text/synonyms.txt)をrevision `830bf9e1313f6f75235ba87ee041e144dbcad8c1`に固定します。[CSV仕様](https://github.com/WorksApplications/SudachiDict/blob/830bf9e1313f6f75235ba87ee041e144dbcad8c1/docs/synonyms.md)の展開制御フラグを尊重します。

| フラグ    | 処理                                                 |
| --------- | ---------------------------------------------------- |
| 空欄／`0` | 展開の起点にも、出力される語にもなる。               |
| `1`       | 出力されるが、そのグループの展開の起点にはならない。 |
| `2`       | 起点にも出力にも使わない。                           |

対象トークンの表層形・正規化形・辞書形と見出しを完全一致で照合し、見出しの大小文字は区別しません。展開は1段だけで、結果を再帰的に展開したり、同義語の組み合わせを総当たりしたりしません。複数トークンからなる見出しは、別の対象語から出力される場合はありますが、トークン境界をまたいで独立に検出しません。分野ラベルによる語義判別も行いません。すべてのローマ字表記や自然言語の同義語を網羅する保証はありません。

## 形式・表示・資源上限

ASIX v1は元から1文書に複数の`texts`を登録できます。補助textはバイナリ形式を変えません。クエリ変換表には別の配信物を使い、任意の位置順位は後述のとおりランタイム境界を拡張します。エンジンは最もよく一致したtextを選び、key単位で結果を重複除去します。基本索引・追加／変更／削除の差分・canonicalな圧縮版には同じ解析済み文書を使い、文書の置換で古い補助表現も消えます。

UIは常にカタログの質問原文を表示します。別のtextに一致した場合は、**検索用表現**の行を分け、そのtext自身の範囲でハイライトします。別名の位置を原文に適用しません。IMEの未確定入力も`input`イベントで検索し、確定・キャンセル時は最終的な入力値へ追従します。入力欄の内容や選択範囲は変更しません。

デモでは内容の更新と索引の集約を分けて表示します。検索例の`更新例`を選ぶと、最初は0件、差分の適用後は変更3件・追加1件の計4件が見つかります（別の1件を削除）。採用成功後のカタログ比較から追加・変更を判定し、色だけでなく文字ラベルも付けます。圧縮後も最初のカタログからの変化としてラベルを保ち、索引ファイル数は2つから1つになります。意図表現モードの結果には質問カタログの更新ラベルを付けません。圧縮版への切替では、同じ検索内容をサーバーで単一索引に集約したものを読み込みます。

**差分前に戻す**ボタンは、Workerを再起動せず入力を保ったまま、初期の索引とカタログへ原子的に戻します。更新ラベルを消し、差分を再び適用できます。復元に失敗した場合は現在の結果を維持します。検索のepochは表示上の世代とは独立に増加させ、以前の採用結果が復元後の表示を上書きしないようにします。

標準の追加上限は文書あたり同義語256件、文書全体131,072 UTF-16単位です。`policy.json`の`maxSynonymTexts`・`maxDocumentUnits`は、それぞれ`-1`でその追加上限を解除できます。ただしASIXのtextあたり65,535単位は維持します。デモの解析呼出しは入力16 MiB・出力64 MiB・20,000レコード・120秒が上限です。ネイティブCLI側にもJSONL入力合計64 MiB／1行1 MiBの制限があります。Rust CLIの上限と既存Workerのメモリ／クエリ上限も維持します。上限で補助表現を黙って切り捨てません。

同義語の件数上限は、原文・正規化語・読み・ローマ字の後に追加する一意なtextだけを数えます。重複する辞書項目や基本表現と同じ同義語は件数を消費せず、文書単位数は最終的な全textを1回ずつ数えます。

Sudachiには、入力プラグイン適用前の原文49,149 UTF-8バイトと、入力変換後65,535 UTF-8バイトの上限もあります。ASIXのUTF-16単位とは別のバイト制限で、`-1`でも維持します。例えば「あ」16,384字は原文のバイト上限を超えます。短い原文でも入力正規化による展開で変換後の上限を超える場合があり、どちらも切り捨てずに失敗します。

## 再現と来歴

[通常のセットアップ](../../README.ja.md)後、オフライン解析用の環境を用意します。

```sh
mise exec -- pnpm analysis:prepare
mise exec -- pnpm analysis:test
BASE_PATH=/asearch-demo/ mise exec -- pnpm build
```

`analysis:prepare`がシステム辞書・フィルタ・同義語・ライセンス資料をSHA検証付きで取得し、Rustのリソース変換器を実行します。`unzip`と解析コマンドを持つRelease版CLI（v0.3.0以降）が必要です。その後の解析はオフラインです。大きいシステム辞書はSudachiがmmapし、ハッシュ付きの不変ファイル名で保存します。stop／同義語の変換済みJSONはRustが所有するコレクションへ読み込み、追加のmmap層を設けません。

`mise exec -- pnpm analysis:update`でSudachiDictとelasticsearch-sudachiの現在のdevelopを解決し、3種類のテキストリソースと帰属情報を取得します。Rust変換が成功してから`resources.lock.json`を更新・準備するので、差分をレビューしてcommitしてください。通常のビルドで上流の最新版へ暗黙に追従しません。システム辞書バイナリの版は別の固定値として管理し、テキストの更新で大きなバイナリも自動交換することはありません。

Rustの公開前に明示的に検証する場合は、`ASEARCH_ANALYZER_CLI`へビルド済みネイティブCLIを指定できます。隣接checkoutは暗黙に参照せず、実行ファイルのSHA-256を記録します。CIでは検証済みのRelease AssetsのCLIを使います。未加工の`public/data/questions.jsonl`とそのデータセットハッシュは維持し、`documents.jsonl`は原文だけを使うCLI入力例として残します。配信用の補助表現付きASIXは別途生成します。

準備では変換前にpinファイルとCLIを取得し、検証済みテキストの専用コピーを変換します。最後の確認でpinやCLIの変更を検出した場合は、以前の準備済み参照を維持して失敗します。公開処理は整合する準備済み情報・pin・policy・変換済みリソース・CLIを一度だけ取得し、base・差分・圧縮・来歴で同じ世代を共有します。CLIの実行には取得済みバイト列の専用コピーを使い、その後の更新は次の公開処理から反映します。ライセンスの選択にも同じpinを使います。取得済みの世代がまだ実行可能な間は、古いハッシュ付きシステム辞書も変更・削除しません。

サイトの`data/analysis.json`へ、同義語のrevision・サイズ・SHA-256・フィルタ設定・変換済みリソースのSHA・ネイティブ解析CLIのSHAを記録します。`licenses/SudachiDict-LICENSE-2.0.txt`と`licenses/SudachiDict-LEGAL`へライセンス・帰属情報を同梱し、フィルタの帰属情報は`licenses/elasticsearch-sudachi-LICENSE`へ置きます。AutoWikiQA自体のCC BY-SA 4.0については[データの出典](data.md)を参照してください。

実辞書の回帰テストでは、Beatlesの双方向対応、展開フラグ、フィルタ、追加上限の解除、ASIX読み込み、差分による旧表現の無効化、圧縮を検証します。Playwrightでは7種類の表記、原文表示、合成IMEイベントを3ブラウザエンジンとモバイルプロファイルで確認します。実機やOSのIME自体を検証するものではありません。

## 質問数とブラウザの予算

2026-10-24に固定shardを同じ解析設定で検証した結果です。検索用textは原文・補助表現の文字列であり、形態素トークンや検索結果の件数とは異なります。

| 質問数 | 検索用text数 | 基本ASIXのバイト数 | gzip-9のバイト数 |
| ------ | ------------ | ------------------ | ---------------- |
| 10,000 | 120,629      | 8,454,336          | 2,534,502        |
| 50,000 | 574,363      | 40,632,640         | 12,554,444       |

gzip-9はオフラインでの圧縮サイズです。CDNがその圧縮方式で配信することを確認した値ではありません。

50kでは読み取り専用WASMの64／128 MiB予算で失敗し、256 MiB設定でChromium・Firefox・WebKitの読み込み・検索が成功しました。これはRustの資源予算の設定値であり、ブラウザ全体のRAM使用量ではありません。公開WASM v0.1.0とv0.2.0の解析コードを組み合わせ、ASIX v1互換性も確認しています。

配信用デモは10kを維持します。50k化には、取得処理の件数上限、カタログの20k件制限、8 MiBの転送上限、世代切替時の余裕を別途評価する必要があります。今回のエンジン単体検証は、50kのUIやモバイルのメモリを保証するものではありません。サーバー解析はバッチ化でき、今回も20k／20k／10kの出力を結合して1つのASIXを生成しました。過去のチューニング結果は記録された索引形状に対するものであり、補助表現を追加した索引へそのまま当てはめません。

## クエリ専用の変換表と順位（Rust 0.3以降）

配信物の生成では同じスナップショットのネイティブ解析器から`asearch-query-rules/1`形式のJSONを1つ出力し、基本・差分・圧縮版の全段階で共有します。`release.json`は不変ファイルとSHA-256を参照します。Workerは検索可能になる前に最大2 MiBを検証し、Sudachi辞書はブラウザへ配信しません。

サーバーは、フィルタ済みコーパスに正規化形が存在する、曖昧でない動詞・形容詞の活用形だけを出力します。ブラウザは単独または空白区切りのクエリの語ごとに1回だけ完全一致の変換を行い、`食べた`・`食べました`・`食べる`は同じ正規化クエリで検索します。未知語・曖昧な形は元のままです。文の分かち書きは行わず、任意の空白のない文、否定形、名詞内の部分文字列は変換しません。上限は活用形50,000規則、かな8,192規則、クエリ・各活用形128 UTF-16単位で、同義語ポリシーの`-1`指定とは独立しています。

上限付きのかな最長一致表で正規化後のクエリが変わる場合は、元のクエリに一致があっても、元とローマ字の両方で検索します。例は`びーt`→`bi-t`と`にh`→`nih`です。候補は重複排除し、編集距離、一致開始位置、order、keyの順に並べ、順位が完全に同じ場合は元の検索を優先します。説明には採用された検索のクエリとrefを使い、入力文字列と選択範囲は維持します。

照合は最大2回、表示は20件です。記事で絞らない検索は各回の候補を最大20件とし、元のセッションは逐次入力の状態を保持、補助検索には一時的なWASMの状態を使います。記事で絞る場合は一時的な状態でカタログ上限内の全一致IDを取得し、記事のフィルタと上位制限より先に統合するため、正確な件数になります。[記事ファセット](data.md#記事ファセット)を参照してください。上位制限で切られた2つの検索に重複がある場合、和集合の正確な件数は確定できません。そのため、件数を加算せず、各検索の件数と取得済みの一意な候補数の最大値を下限として「少なくとも…件一致」と表示します。全一致を取得できた場合と、一方だけが一致した場合は正確な件数を表示します。変換表はサーバーの固定版wana_kanaから生成し、`んあ`→`n'a`のようなアポストロフィも含みます。MITライセンス表示は`licenses/wana_kana-MIT.txt`として配布します。変換後に上限を超える場合は再検索しません。

コーパス検索はRustの全候補を対象とする`(最小編集距離, 最も早い正規化UTF-16開始位置, order, key)`の順位を明示的に使います。上位件数へ絞る前に、生存するすべての一致別名を評価するため、同じ距離なら語頭一致が後方の部分一致より上位になり、オフセット1は2より上位になります。意図表現モードは従来の順序を維持します。[順位の契約](https://github.com/tkhshtsh0917/asearch/blob/main/docs/ja/ranking.md)を参照してください。位置評価のDPと整列の処理が増え、従来の性能計測には含まれません。

これらの機能にはCLI・WASMとも0.3以降が必要です。公開前のローカル検証では開発用成果物を明示的に指定し、未公開Assetsのハッシュを捏造したり、ローカル検証をPages配信と混同したりしないでください。

配信物の生成では、変更後の版も含めて全段階の質問原文を重複排除し、クエリ出力だけに一時keyを付けます。実際の結果keyは変えません。20,000原文の上限は結果文書数やASIX text数ではなく、異なる原文の版を数えます。変換規則はASIX textを増やさず、JSON・JavaScript変換MapのメモリはRust作業予算の外です。

クエリ変換表の2 MiB上限は、最終的なUTF-8レスポンスbodyのバイト数に適用します。配信物の生成では末尾に改行を加えず、ファイル名とダイジェストを決める前に超過を拒否します。上限ちょうどのbodyはWorkerも受け付けます。
